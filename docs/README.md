# docs/

このフォルダには、コードと一緒に変わる文書を置く。仕様書（`specs/`）と、アプリの設計判断（`decisions/`）。
開発環境や進め方の判断、計画、振り返りはここには置かない（リポジトリの外で管理している）。

## 構成

| パス | 中身 |
| --- | --- |
| `specs/` | 機能ごとの仕様書。1機能＝1ファイル（例：`group-message.md`） |
| `specs/_template.md` | 仕様書のテンプレート |
| `decisions/` | アプリの設計判断（ADR）。`NNNN-タイトル.md` の形で、0001から番号を振る |
| `decisions/_template.md` | ADRのテンプレート |

## 仕様書のルール

1. **仕様は実装の前に書く。** 受け入れ条件を人が確定し、`status: approved` になってから実装を始める。
   - 下書きはAIに任せてよい。受け入れ条件を確定するのは人。
2. **受け入れ条件は、テストケースにそのまま落とせる粒度で書く。** 1行が1テストに対応するのを目安にする。
3. **仕様と実装が食い違う変更をするときは、同じPRで仕様書も更新する。**
   - 仕様を正として実装を直すか、実装に合わせて仕様を直すかは人が決める。
   - AIは、仕様と食い違うことに気づいたら、実装する前に報告する。
4. 仕様書がない機能は、実装する前に仕様の下書きから始める。
5. 仕様の中身は `CLAUDE.md` に書き写さない。`CLAUDE.md` には、仕様書の場所と読むタイミングだけを書く。

## status の意味と更新するタイミング

| status | 意味 | 変えるタイミング | 変える人 |
| --- | --- | --- | --- |
| `draft` | 書いている途中。まだ実装してはいけない | 新しく作ったとき | AIまたは人 |
| `approved` | 受け入れ条件が確定した。実装してよい | 人が受け入れ条件を確認し終えたとき（PRでマージ） | 人 |
| `implemented` | 仕様どおりに実装され、main に入った | 実装PRをマージするとき（**同じPRで**変える） | 実装した人・AI |
| `deprecated` | もう使わない仕様。ファイルは消さずに残す | 機能を廃止した、または別の仕様に置き換えたとき | 人 |

- status を変えるときは、`updated` の日付も更新する。
- フェーズを終えるときに、status が実装と合っているかを確認する（実装済みなのに `approved` のまま、になっていないか）。

## ADR（decisions/）のルール

- ADRに書くのは、アプリの設計判断のうち**あとから変えるとコストが大きいもの**だけ。
- 番号はこのリポジトリの中で0001から振る。Vault側のADRとは別の番号なので、話すときは「リポジトリ側の0001」のように区別する。
- `accepted` になったADRは書き換えない。判断を変えるときは新しいADRを作り、古いADRのほうは `superseded` にする。
- `accepted` にするのは人。

## テンプレートを変えるとき

`decisions/_template.md` は、Vault側のADRテンプレート（`90_Templates/adr.md`）と同じ見出し（状況・決定・検討した選択肢・結果）を使う。**見出しを変えるときは、両方のテンプレートを直す。**
