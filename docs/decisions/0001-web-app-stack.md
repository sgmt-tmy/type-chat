# 0001 Webアプリの技術選定

## 状況(Context)

type-chat を、ブラウザから操作できるWebアプリにする（親Issue #133）。現在のコードは、ドメインの純粋関数（`src/group.ts`・`src/message.ts`・`src/user.ts`）とそのテストだけで、画面・API・永続化・リアルタイム配信はまだない。

これから書く仕様書と実装は、構成・永続化・UI・配信方式・層構成を前提にする。いずれもあとから変えるとコストが大きい判断なので、実装の前にここで決めて記録する。

前提とする条件:

- 小規模なチャットアプリで、利用者も同時接続も少ない。1台・1プロセスで動けばよい。
- 新着メッセージやグループの変更を、開いている画面にすぐ反映したい（手動の再読み込みや数秒の遅延は避けたい）。
- 認証は最小限（当面は扱わない）。
- 追加するサーバー・ライブラリ・運用の手間は少なくしたい。TypeScript の strict モードを維持する。

## 決定(Decision)

### 構成

- **Next.js（App Router）のフルスタック**にする。画面とAPIを1つのアプリ・1つのプロセスで動かす。
- クライアントからの操作（投稿・変更）は **Route Handler**（`src/app/api/**/route.ts`）で受け、JSONでやり取りする。

### 永続化

- **SQLite + Drizzle ORM** を使う。
- DBファイルは `data/type-chat.db`。パスはコードの定数に置き、環境変数は使わない。

### UI

- **Tailwind CSS + shadcn/ui** を使う。

### サーバー→クライアントの配信

- 新着メッセージ・グループの変更は **Server-Sent Events（SSE）** で配信する。
- 定期的な再取得（**ポーリング**）は使わない。
- SSE のイベントは、**単一プロセス内のイベントバス**で配る。複数プロセス・複数台への水平分散はしない。

### 認証

- 認証は扱わない（将来課題）。利用者の識別は認証ではないため、公開環境では運用しない。

### 層構成とディレクトリ

依存の向きは上から下へ。下の層は上の層を知らない。

| 層 | 置き場所 | 責務 |
| --- | --- | --- |
| ドメイン | `src/*.ts` | 集約を受け取り、新しい集約を返す純粋関数。I/O を持たない |
| リポジトリ | `src/db/` | Drizzle で集約をロード・保存する |
| ユースケース | `src/server/` | ロード → ドメインの純粋関数 → 保存 → イベント発行 |
| Route Handler | `src/app/api/` | HTTP（JSON）とユースケースの間の変換。SSE のストリームもここで返す |
| 画面 | `src/app/`・`src/components/` | ページとUIコンポーネント |

## 検討した選択肢

### 構成

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **Next.js（App Router）フルスタック（採用）** | 画面とAPIを1つのアプリ・1プロセスで動かせる。型を画面とAPIで共有しやすい。Route Handler で SSE（`ReadableStream`）を返せる | WebSocket の Upgrade を標準で扱えない。フレームワークの規約（App Router）に従う必要がある |
| API サーバー（Express・Fastify など）+ SPA（Vite + React など）の分離 | 層の境界が物理的に分かれる。APIサーバー側で WebSocket も扱いやすい | プロセス・ビルド・デプロイが2つになる。CORS やオリジンの扱いが増える。この規模には過剰 |
| サーバーサイドレンダリングのみ（テンプレートエンジン + フォーム送信） | 依存が少ない | 画面の部分更新やリアルタイム反映を手で組む必要があり、UIの部品化もしにくい |

### 永続化

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **SQLite + Drizzle ORM（採用）** | DBサーバーが要らず、ファイル1つで動く。Drizzle はスキーマを TypeScript で書け、型推論が strict モードと相性がよい。生成物（クライアントのコード生成）が要らない | 書き込みの同時実行性は低い。複数台からの共有には向かない |
| SQLite + Prisma | 普及していて資料が多い | クライアントのコード生成とエンジンのバイナリが必要。この規模には重い |
| PostgreSQL（+ Drizzle など） | 同時実行性・拡張性が高い | DBサーバーの用意と運用が必要。この規模には過剰 |
| JSON ファイルなどへの自前の保存 | 依存がない | 同時書き込み・クエリ・スキーマ変更を自前で扱う必要がある |

### リアルタイム配信

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **Server-Sent Events（採用）** | サーバー→クライアントの一方向に十分。Route Handler の通常のHTTP応答（`ReadableStream`）で実装でき、追加のサーバー・ライブラリが要らない。ブラウザの `EventSource` が再接続を自動で行う。Cookie が通常のリクエストと同じく送られる | 一方向のみ。HTTP/1.1 では同一オリジンの同時接続数の制限を受ける。長時間の接続を保てない環境（サーバーレス）には置けない |
| WebSocket | 双方向・低遅延 | Next.js の Route Handler は WebSocket の Upgrade を標準で扱えず、カスタムサーバーか別プロセスが要る。再接続を自前で書く（またはライブラリを足す）必要がある。この用途では双方向は要らない |
| ポーリング（定期的な再取得） | 実装が最も単純。長時間の接続が要らない | 間隔の分だけ反映が遅れる。変化がなくてもリクエストが発生し続け、無駄が多い |
| ロングポーリング | 普通のHTTPで、ポーリングより遅延が小さい | 応答のたびに接続を張り直す必要があり、取りこぼしの扱いも自前になる。SSE で同じことがより簡単にできる |

### SSE を選び、WebSocket を選ばない理由

- 必要なのは、サーバー→クライアントの**一方向だけ**（新着メッセージ・グループの変更の通知）。クライアントからの操作は Route Handler への通常のリクエストで送るので、双方向の通信路は要らない。
- SSE は Route Handler の通常のHTTP応答（`ReadableStream`）で実装でき、**追加のサーバー・ライブラリが要らない**。Next.js の Route Handler は WebSocket の Upgrade を標準で扱えず、WebSocket を使うにはカスタムサーバーか別プロセスが要る。
- ブラウザの `EventSource` が**再接続を自動で行う**。
- SSE は通常のHTTPリクエストなので、**Cookie が通常のリクエストと同じく送られる**。将来、認証を入れるときも同じ仕組みに載せられる。

### ポーリングを使わない理由

- 間隔の分だけ**反映が遅れる**。遅延を小さくしようと間隔を詰めると、リクエストが増える。
- 変化がなくてもリクエストが発生し続け、**無駄なリクエスト**がサーバーとクライアントの両方の負荷になる。

## 結果・影響(Consequences)

- **単一プロセス前提**になる。SSE のイベントはプロセス内のイベントバスで配るため、複数プロセス・複数台に分けると、別のプロセスで起きた変更が届かない。水平分散が必要になったら、プロセス間でイベントを配る仕組み（Redis の Pub/Sub など）を入れる判断を、新しいADRで行う。SQLite のファイルも1台で使う前提である。
- **接続時間に制限のあるサーバーレス環境には置けない**。SSE は長時間の接続を保つ必要があるため、常駐するNode.jsのプロセスとして動かす。
- **SSE の接続は1タブ1本**（利用者単位のストリーム）にする。HTTP/1.1 ではブラウザが同一オリジンへの同時接続数を制限する（一般に6本程度）ため、グループごと・画面の部品ごとにストリームを開くと、ほかのリクエストが詰まる。1本のストリームで、その利用者に関係するイベント（新着メッセージ・グループの変更）をまとめて配る。
- **認証がないため、公開環境では運用しない**。利用者の識別は認証ではなく、なりすましを防げない。公開する前に、認証を別のADR・仕様書で決める。
- 以降の仕様書と実装は、この層構成（`src/*.ts` → `src/db/` → `src/server/` → `src/app/api/` → `src/app/`・`src/components/`）とディレクトリを前提にする。ドメインの純粋関数は I/O を持たないまま保ち、既存のテストはそのまま使う。
- 依存として Next.js・React・Drizzle ORM・SQLite のドライバ・Tailwind CSS・shadcn/ui を追加することになる。追加は実装のタスクで行い、このADRでは行わない。
- `data/type-chat.db` はコードの定数で指すため、置き場所を変えるにはコードの変更が要る。環境ごとに切り替える必要が出たら、そのときに判断する。
